# Getting Started with PathWave Data Tools[](#Getting-Started-with-PathWave-Data-Tools "Link to this heading")

## Introduction[](#Introduction "Link to this heading")

**PathWave Data Tools** (pwdatatools) is a Python library that makes it easy to work with many types of data, including simulated and measured data.

It supports reading and writing of many popular data file formats.

| File Format | Description | Typical File Extensions | Read | Write |
| --- | --- | --- | --- | --- |
| PathWave Data Tools native files | A binary datafile format with great performance and robust metadata storage. Supports any arbitrary number of levels of hierarchy | .pwdt | Yes | Yes |
| PathWave Advanced Design System (ADS) datasets | Keysight’s proprietary binary dataset format for ADS. Supports one level of hierarchy | .ds | Yes | Yes |
| MDM (Measured Data Management) datafiles | Text format used by various Keysight modeling and measurement software such as IC-CAP, WPE, MBP, MQA, and PD1000A. Not hierarchical | .mdm | Yes | No |
| PathWave System Design (SystemVue) datasets | Keysight’s proprietary format, stored within SystemVue workspaces. Each dataset supports one level of hierarchy | .wsv | Yes | No |
| Generic MDIFs (Measurement Data Interchange Format) files | A popular, general-purpose text format. Supports one level of hierarchy | .mdf .mdif | Yes | Yes |
| Comma-separated values (CSV) files | Comma-delimited text format (tab-delimited files also supported). Not hierarchical | .csv | Yes | Yes |
| CITI (Common Instrumentation Transfer and Interchange) files | A general-purpose text format. Supports one level of hierarchy | .cti .citi | Yes | Yes |
| S2PMDIF files | A specialized MDIF format for S-parameters. Supports one level of hierarchy for noise parameters | .s2p | Yes | No |
| Touchstone files | The most popular text format for S-parameters. Supports one level of hierarchy for noise parameters | .snp .ts | Yes | Yes |
| SMatrixIO files | A highly-efficient Keysight proprietary binary format for S-parameters. Not hierarchical | .sio | Yes | Yes |
| Load Pull datafiles | Supports many formats from Keysight, Focus, and Maury measurement systems. Not hierarchical | .cst .lp .lpacwave .lpc .lpcwave .lpd .lpwave .mat .sat .satwave .spl | Yes | No |
| Electromagnetic far field datafiles | Supports Keysight’s ffio format and the HFSS ffd format. Not hierarchical | .ffio .ffd | Yes | No |

There are two primary objects that are used to organize data: the `Group` and the `Block`.

![Groups and Blocks](../../_images/Group_and_Block_illustration.png)

## Side Topic: Best Practices for Retrieving Blocks from Groups[](#Side-Topic:-Best-Practices-for-Retrieving-Blocks-from-Groups "Link to this heading")

The reason for the squiggly line is that a Group’s members may be Blocks or other Groups, so the IDE doesn’t know whether we retrieved a Group or Block. Therefore, it doesn’t know if there is an attribute `ivarnames`. So, for production code, it is recommended to instead use the method `Group.get_member_as_block` to retrieve a Block so that the IDE (including type checkers) can be of more help to you.

```
[6]:
```

```
mcblock = group.get_member_as_block(
    1
)  # <= this retrieves the same Block we retrieved before using square bracket indexing
mcblock.ivarnames  # <= the IDE now knows this is a Block... no more squiggly line
```

## Summary of Some Useful Block Methods for Data Manipulation[](#Summary-of-Some-Useful-Block-Methods-for-Data-Manipulation "Link to this heading")

There are several useful methods to modify Blocks listed below, most of which we we won’t exercise in this example.

| Method | Description |
| --- | --- |
| Block.drop\_observations() | Remove observations where a condition is True. |
| Block.drop\_vars() | Remove the specified variables. |
| Block.fill\_nan() | Fill NaN values. |
| Block.fill\_null() | Fill null values. |
| Block.iter\_sweep\_nodes() | Iterate over ivar value combos (or their idxs). |
| Block.keep\_observations() | Keep the observations where a condition is True. |
| Block.keep\_vars() | Keep only the specified variables. |
| Block.pop() | Remove and return a variable by name. |
| Block.rename\_vars() | Rename variables. |
| Block.set\_data() | Replace the data for variable(s) in the Block. |
| Block.sort\_observations() | Sort observations using desired indices. |
| Block.sort\_observations\_by() | Sort observations by values of specified variable(s). |

## Writing a Block to a File[](#Writing-a-Block-to-a-File "Link to this heading")

Let’s write out our combined S-parameter data to a new file. We cannot write it to a Touchstone file because Touchstone only supports 1 independent variable (frequency) and we have two ivars (batch\_number and freq). So, let’s write our data to a CSV file. We can use the `Block.to_file` method to write any type of supported datafile. If the file extension is recognized, it will automatically choose the appropriate format. Here, .csv is a recognized extension, so a CSV file is produced.

By default, pwdatatools is in “exclusive write” mode. This means that it will not overwrite existing files. In order to overwrite an existing file, you must use `dst_mode='w'` in the `Block.to_file` method.

```
[41]:
```

```
block_combined.to_file("combined_s_params.csv", dst_mode="w")
```

We can easily choose to write out to other supported formats, like MDIF and ADS datasets. If we use the standard recognized file extensions, the correct format is automatically produced.

```
[42]:
```

```
block_combined.to_file("combined_s_params.mdif", dst_mode="w")
block_combined.to_file("combined_s_params.ds", dst_mode="w")
```

group_s_params_and_mc = pwdt.Group([block_combined, mcblock, vblock])
